# Provider credentials

Signed-in users can save a Gemini, Groq, OpenAI, or Anthropic chat key and model in Settings. OpenAI uses the OpenAI-compatible Chat Completions API adapter; Anthropic uses its Messages API with structured JSON outputs. Changeweft also supports an optional Google AI Studio key for Gemini Embedding 2, which is used for repository import and semantic search regardless of the selected chat provider. Keys are encrypted with AES-256-GCM before database storage. The encryption key is derived from `NEXTAUTH_SECRET` with HKDF-SHA256, and the user ID is authenticated as associated data so ciphertext cannot be moved between accounts. Key values are never included in the Settings page response or application logs; they are decrypted server-side only for provider calls.

Changing `NEXTAUTH_SECRET` makes previously stored credentials undecryptable. Users must re-enter their keys after such a rotation. Removing personal settings deletes their saved ciphertext and returns to the optional server defaults (`AI_PROVIDER`, `AI_API_KEY`, `AI_MODEL`, and `EMBEDDING_API_KEY`). The application does not validate a key with a provider when it is saved; provider errors appear when the next relevant operation runs.

The Settings form accepts only the Gemini, Groq, OpenAI, and Anthropic chat adapters. It does not accept a custom endpoint, so user input cannot redirect provider requests to arbitrary hosts. Repository embeddings remain fixed to Gemini Embedding 2 and 768 dimensions. OpenAI API access and billing are separate from ChatGPT subscriptions.

## Repository and workflow ownership

Each imported repository is associated with the authenticated GitHub account ID. A repository's files, code chunks, and workflows are reached only after a server-side ownership check. Workflow pages and actions verify ownership through the workflow's repository; pull-request creation repeats that check before using the signed-in user's GitHub token. Analytics joins each metric back to owned repositories so one account cannot see another account's activity.

The app uses GitHub's stable `providerAccountId` as its account key. Auth.js otherwise creates a fresh random user ID for OAuth sign-ins when no database adapter is configured, which would make repository and workflow ownership change after every sign-in. Older workspaces created with those transient IDs can be reconnected only after GitHub verifies that the signed-in account personally owns the exact repository. Reconnection updates the workspace and its workflow ownership in one transaction; saved AI credentials are re-encrypted for the stable account key when their prior key is available.

The repository migration leaves pre-existing repository rows unassigned until a user restores them. The restore action verifies the signed-in GitHub account and requires the GitHub API to confirm that the account personally owns the exact repository ID. A matching public repository name alone is not enough. Workflow ownership is backfilled from each workflow's `REQUIREMENT_CREATED` event actor. When that legacy actor is a display name or login instead of the current Auth.js ID, recovery maps only matching labels from the verified GitHub profile to the current account. Workflow pages and analytics check both repository ownership and workflow creator. Unmatched workflows remain inaccessible.
